# Current STATIC renderer genesis composition

[StreamFullV1StaticRendererPlan](../../script/current/StreamFullV1StaticRendererPlan.sol)
constructs the original `StreamRendererV1`, its original
`StreamStaticAttributionCompanion`, and `StreamRendererRegistryModule`. They use
the current Core, Router, MetadataV1, SchemaRegistry, Artist, original finality
registry, entropy coordinator and Executor. The planner preserves the renderer's
immutable source bindings and the registry's closed target roles.

## Observed deployment stages

1. Supply a `Configuration` whose schema and renderer manifest hashes identify
   the actual retained documents. Gas inputs are explicit deployment choices;
   fixture values do not establish normative gas floors.
2. Call `deployRenderer` after every original source, including the finality
   registry, has been deployed. This constructs the original attribution
   companion and renderer. No Core pointer is changed.
3. Build the deployment's reviewed, sorted named-target inventory, then call
   `deployRegistry`. The registry pins the inventory once. The planner requires
   the original Core, MetadataV1, Router, entropy coordinator, attribution
   companion and linked static encoder. It also requires the configured
   dependency registry when nonzero. A zero dependency registry means that this
   renderer cannot serve dependency-registry bundles; it creates no catalog row.
4. Admit the three returned `operatingPolicies` through the canonical catalog
   extension: renderer registration and the two hosts' gas-parameter raises.
   Execute catalog extension before preparing later actions against its new
   revision. Deprecation needs a separate class0 policy and isolated delayed
   tightening classification; this construction slice does not prepare it.
5. Register the two genuine ERC165 `registrations` with the canonical
   SystemManifest tail. The attribution companion has no ERC165 module surface
   and is retained as an explicit support identity, never a fictitious row.
6. Register the exact schema, context, manifest, analysis and golden catalogs in
   the original SchemaRegistry. The context document ID must match the original
   renderer's `STREAM_CONTEXT_V1`. Use `admission` to derive the registry's exact
   class1 scope and old/new commitments, then schedule and execute through the
   real Executor. The registry checks retained evidence and actually calls the
   renderer for each supplied golden vector.

The returned products retain deployment observations for later stages. These
checks detect changed bindings; compiler-source review must independently
authenticate the runtimes.

## Read and evidence boundaries

The planner checks necessary direct targets, not the complete transitive read
closure. Supply the proposed deployment's exact reviewed target/read inventory.
Artist and finality reads behind the attribution companion require their own
source and runtime review; unrelated hosts must not be relabeled
`METADATA_COMPANION`. OwnerRecords remains outside the default MARKETPLACE
read set. See [renderer registration evidence](static-renderer-versions.md) and
[STATIC routing](static-metadata-routing.md).

No reviewed analysis report or complete golden inventory is generated by this
planner. An ABI-encoded analysis assertion alone does not establish opcode or
read-set conformance. Release admission still needs the genuine analysis of
the exact renderer and its transitive paths, plus the required normative golden
inventory.
