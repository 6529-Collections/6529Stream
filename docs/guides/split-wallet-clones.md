# Split wallet version 4 and genesis role 6

The current SplitFactory deploys one locked StreamSplitWallet implementation during
its constructor. Read `splitWalletImplementation()` and
`splitWalletImplementationCodeHash()` from that actual factory to populate genesis
role 6. Do not deploy a second implementation for the manifest. The factory's
constructor arguments are unchanged; the new companion capability is
`IStreamSplitWalletImplementation`.

A profile's wallet is now a deterministic clone. The original profile domain and
field order remain, including the chain, factory, schema, wallet version, both
code hashes, asset-policy registry, canonical entries and metadata. The changed
representation uses wallet version **4**. Published version-3 factories, IDs,
predictions and release evidence remain historical identities; they are not
relabelled or migrated by this change.

## Deployment and initialization

The factory creates its implementation with ordinary CREATE. That runtime embeds
the exact factory and implementation addresses as immutables. Implementation
storage is locked at construction and cannot be initialized as a user wallet.
Each clone has zeroed independent storage until the factory initializes it in the
same transaction as CREATE2. The initializer requires the embedded factory,
an existing profile and the factory's exact predicted address. `walletFor` uses
the CREATE2 formula independently of the stored wallet field, which is published
only after initialization succeeds. A failed initializer rolls back deployment.

The creation code is a ten-byte copy/return prefix followed by the exact 52-byte
runtime. That runtime adds a five-byte empty-calldata branch and a final STOP to
the fixed [ERC-1167 delegate/return sequence](https://eips.ethereum.org/EIPS/eip-1167).
It is an explicitly defined variant, not the standard's byte-identical 45-byte
runtime. Empty-calldata native deposits make no storage access or external call;
nonempty calls delegate only to the embedded immutable implementation and copy
its full return or revert bytes. There is no upgrade, beacon or target setter.

The factory pins the implementation runtime and refuses new deployment or wallet
recognition if that pin changes. It also retains exact clone runtime and original
profile-field validation. Implementations differ across factory addresses, so the
init/runtime hashes are fixed per deployed factory and are exposed by **view**
getters. Their selectors are unchanged, but Solidity clients declaring calls as
`pure` must adopt the current interface. Offchain callers must read hashes from
the intended factory, not assume a universal clone hash.

## Payments and releases

Prefunding the predicted address with native ETH or an approved ERC-20 remains
possible. The clone retains the original cumulative accounting, recipient
entitlements, asset-policy checks and failure rollback. Release EIP-712 names,
version, fields and replay keys are unchanged; the verifying contract is the
individual clone. A signature for the implementation or another wallet does not
authorize that clone. The inherited reentrancy guard admits its first call from
zeroed clone storage, then uses the original entered/not-entered states.

## Validation boundary

`StreamSplitWalletClones.t.sol` covers the actual singleton, locked initialization,
exact clone bytes and CREATE2 identity, version separation, prefunding, a cold
2,300-gas native deposit, return/revert transport, failed initialization and an
identical 2-of-2 Safe CALL retry after a recipient rejects payment. The two existing
wallet suites retain native/ERC-20 accounting, callback and signature-replay
controls, including real Safe 1.3.0, 1.4.1 and 1.5.0 bytecode. The initializer-input harness
exists only to reach invalid inputs that the canonical production factory never
supplies; implementation drift uses an explicit test-only code substitution.

These focused tests use actual Factory, Wallet and AssetPolicyRegistry contracts,
with the existing typed governance and token-failure fixtures. They do not prove a
complete current-Core/Artist/genesis launch graph. Native results and production
runtime/init-code sizes are recorded in the source-bound handoff; authored cases
alone are not runtime evidence. Existing release artifacts are not regenerated by
this source feature batch.

The source-bound focused run passed all **84 tests** (49 original wallet,
25 original authorization, 10 clone-specific). The first run's one failing
negative fixture is retained; its correction reads the profile before deliberately
replacing implementation code and changes no production source. The final capture
contains 31 sources, with 66 artifact metadata records and 954 matching source-hash
comparisons. Solc 0.8.19, via IR, optimizer 200, Paris produced seven fitting
production products. Factory runtime/init sizes are 9,684/12,520 bytes, implementation
9,294/9,411, and linked deployment worker 10,123/10,157. The deployed clone itself
is 52 bytes. Those measurements belong to this focused compilation context.
